1 · Understand

How it works

Four steps. Nothing changes in your task until step 3.

  1. 1

    Pick one

    Choose the integration for the service that your task uses.

    integration:add <name>
  2. 2

    Read the plan

    The CLI shows every setting that it will write, and what you must add yourself.

    --dry-run
  3. 3

    Answer y

    It installs the package and writes task.yaml. Any other answer changes nothing.

    Apply? [y/N]
  4. 4

    Finish and deploy

    Add your secret values and hosts, check the task, and deploy.

    task:deploy

2 · Read the plan

The plan tells you everything first

This is the plan for stream on a new Node task. It has four parts. Point at a part to see its lines.

  1. 1

    What you get

    The package, and what it brings: settings, code, and the system program that it runs (here ffmpeg).

  2. 2

    What it writes

    a -> b raises a setting. + adds a setting. A setting is never lowered.

  3. 3

    What you add

    The part that is different for each user, so the CLI cannot write it. You add it after the apply.

  4. 4

    The result

    With --dry-run, the command stops here. With no --dry-run, it asks Apply? [y/N].

<version> is the latest version of the integration. The yellow lines are always yours: the same colour marks your steps below.

3 · Know your part

What it does, and what you do

An integration writes what is the same for every user. You add what is different for you.

The integration

  • Installs one npm packageAs a normal dependency. Your lockfile pins the exact version.
  • Writes the settingsNetwork type, preset, ports, routes, system packages, and the names of the secrets.
  • Gives you the codeYou import it in your task, the same as any other package.

You

  • Set the secret valuesIt writes only the names. The values go to the platform with secret:set, and never into task.yaml.
  • Add your hostsYour bucket or source host is different for each user, and an integration cannot ask for a wildcard host.
  • Call the code, check, deployYou decide where your task uses it. Then task:validate and task:deploy, as usual.

4 · Try it

Add your first integration

Give a task a place to keep big results: add s3-storage to a Node task, then check it and deploy it. Each output comes from a real run.

APrepare

  1. Get the CLI

    You need the ignitify CLI 1.2.0 or later, installed and signed in. See Install.

  2. Create a Node task

    An integration needs a package.json in the task folder. task:create writes one. You can also use a Node task that you have. See Your first task.

BAdd the integration

  1. Read the plan

    With --dry-run, the command shows the plan and stops. Nothing in the task changes.

  2. Apply it

    Run the command again with no --dry-run, and answer y. It installs the package and writes task.yaml. Your comments and the order of your keys stay.

CAdd your part You add

  1. Store the secret values

    The plan wrote the secret names. You set the values. Each command reads the value from stdin, so it stays out of your shell history. See Use secrets.

  2. Add your bucket host

    The task had no network, so the plan wrote egress_allow: []: the task cannot connect to a host yet. Put your bucket host in the list. See Network access.

DUse it and ship

  1. Use it in your code

    Upload a file from the scratch disk and return a download link. The result stays small, also for a big file.

  2. Check the task

    task:validate also checks that task.yaml covers every integration of the task.

  3. Deploy as usual

    The build installs the package from your lockfile, the same as any other dependency.

5 · Keep it working

After you add it

What happens when you say no, edit by hand, add a second integration, upgrade or remove.

Any answer other than y changes nothing

The command stops. No file changes: not package.json, the lockfile, node_modules or task.yaml.

Your edits are fine. task:validate catches a break.

The settings are normal lines in your task.yaml. If someone deletes the secret names, the check fails before a deploy, not during a run:

Settings join. They never go down.

You can add more than one integration to a task. Each plan shows only what it adds to the task that you have.

  • Lists are joinedSecrets, hosts, routes and system packages from each integration are all kept.
  • Levels only go upThe network type and the preset go to the higher value that an integration needs.
  • A conflict stops the commandIt names the field and changes nothing.

The Launch event tutorial uses stream and s3-storage in one task.

Run the same command again

Only the latest version is supported. task:validate warns when your version is old, and names the latest one. integration:add installs the latest version and shows only the new settings. If there are none, it changes nothing:

Uninstall the package

The settings that it wrote stay in task.yaml, because they are yours. Delete the ones that you no longer need, by hand. Then run task:validate.

6 · Trust it

Safe by design

An integration changes only what you can see and read, and only after a yes.

  • A plan before any change

    You see each setting before it is written. "N" or --dry-run changes nothing: not package.json, the lockfile, node_modules or task.yaml.

  • No install scripts

    The package installs with --ignore-scripts, the same as your build. Your lockfile pins the exact version.

  • Conflicts are refused

    A value that the integration cannot use is never overwritten. The command stops and names the field.

  • Your file, your settings

    task.yaml stays the one truth, and the platform enforces only task.yaml. Edit or delete any setting by hand.

  • task:validate checks it

    It finds a task that no longer covers its integrations, for example a deleted secret name or a preset that is too small.

  • Your VM only

    The code runs only in your own task VM, with the secrets and hosts of that task. The build installs it from your lockfile.

Questions

Do I need an integration?

No. An integration is an option. You can write the same settings and code yourself. Each README lists the settings, so you can copy them by hand.

Does my task need to be a Node task?

An integration is an npm package, so the task folder needs a package.json. task:create writes one for a Node task.

What if it conflicts with my task?

The command stops before it changes anything, and names the field. For example, stream needs interaction: continuous. Change the field by hand, or use another task.

What does it cost?

The integrations are free and open source (Apache-2.0). You pay for your runs as usual. Some integrations need a larger preset or inbound traffic: stream needs std.medium and inbound traffic. Check that your plan allows them. See Presets and limits.

Can I suggest an integration?

Yes. Contact us and tell us the service, and the work that you want to stop building.
