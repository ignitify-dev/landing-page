How capacity works

Your plan limits how much work runs at the same time. This page shows the two limits, how a run counts against them, and what happens when one is full.

Two limits on what runs at once

  • Running VMs. Every plan has this limit. It is the number of runs that can be active at the same time, of any size.
  • Units. Only some plans have this limit. Today these plans have it: enterprise (on request). Each active run uses units, and the total must stay at or below the limit.

A new run starts only when it fits under every limit that your plan has. A plan without units (free, starter, team and pro) is not unlimited: its running-VM limit and its list of presets still apply. Presets and limits shows the numbers of each plan.

Each preset has a weight

A weight is the number of units that one run of a preset uses. The smallest preset, std.micro, weighs 1 unit. The weights come from the same preset table that the platform reads.

A weight is not the vCPU or the memory number. It shows how much of a host the preset takes.

A run uses its weight while it is active

A run takes its weight in units when the platform accepts it. It gives the units back when it gets a final status (see Lifecycle and statuses). A run that waits for a host also uses its units.

Runs from a webhook or a schedule count in the same way. A webhook run uses the default preset of your plan, so it uses the weight of that preset.

Mix presets as you like

The limits count runs and units, not presets. You can run many small runs, a few large runs, or a mix. The example below uses the enterprise plan: 240 units and 24 running VMs. Each row shows the active runs, then one more run.

Pinned VMs count on their own

A pinned VM counts against the pinned-VM limit of your plan. An idle pinned VM is not a running VM and uses no units. A run on a pinned VM counts like any other run: it is a running VM and it uses its weight.

When a limit is full

  • The running-VM limit is full: 429 with concurrent-run-quota. The platform checks this limit first.
  • The units are full: 429 with run-unit-quota. A run of a lighter preset can still fit.
  • A host is busy: this is not a plan limit, and it never gives a 429. With --on-busy queue (the default) the run waits for room for a limited time. With --on-busy reject it fails at once.

--on-busy does not wait for a plan limit. A full plan limit refuses the run at once. A webhook gets the same 429, and a scheduled run waits and tries again for a limited time.

Tip

Each refusal names one limit. Read the reason field, not the text. Errors shows a sample of each.

See your numbers

quota shows active_runs against your running-VM limit. On a plan with units, a units line follows it. On a plan without units, there is no units line.

whoami shows the weight of each preset that your plan allows, but only on a plan with units. whoami --json always has the fields: limits.max_units (null when there is no units limit), usage.active_units and unit_weights.

Words on this page

  • Unit: the amount that a run of std.micro uses. A plan with units has a limit on the total.
  • Weight: the number of units that one run of a preset uses.
  • Running-VM limit: the number of runs that can be active at the same time, on every plan.
  • Pinned VM: a VM that stays up between runs. It counts against its own limit. While idle it uses no units; a run on it uses its weight.
