Terraform

Recipes

Short, practical setups. Every sample works with Terraform and with OpenTofu 1.11 or later. Replace the names with your own.

Set up a tenant from zero

The tenant already exists, because it comes from sign-up. This recipe fills it with access, a secret, a task, its code and a hook. Use two root modules, so the daily job never holds the owner key.

1 · Access, with the owner key

Apply this once, by hand. It makes a user, a group and a key for CI.

Read the key once with terraform output -raw ci_key and put it in the secret store of your CI system. Do not print it to a log.

2 · The app, with the user key

CI applies this with the user key from step 1.

The apply makes the secret, the task, uploads and builds the code, then makes the hook. The report folder holds a task config with slug: report and a task that reads DB_PASSWORD. See Your first task.

Roll a code update

Change a file in the task folder, then plan and apply.

  • The apply builds the new deployment first. It deletes the old one only when the new one is READY.
  • The hook keeps its URL and its secret.
  • A failed build keeps the old deployment live. Fix the code and apply again.
  • Runs that are still running on the old deployment end, and its run history is deleted. Apply when no run you need is in flight.

Rotate a secret

Terraform cannot see a write-only value, so a new value needs a new version number.

A task reads the new value on its next run. A VM that is already running keeps the value it started with.

Rotate a user key or a hook

Replace the resource. The new one has a new value, and the old one stops working.

After a key replace, put the new key in your CI store. After a hook replace, give the new URL and secret to the sender.

Bring existing objects under Terraform

You made a task, a secret or a user with the CLI, and now you want Terraform to own it. Write the resource, then import it. The plan must show no change before you apply.

  • Import a task before its deployment and its hook.
  • After an import of a key or a hook, the raw key or secret is empty. Replace the resource to get a new one.
  • A secret with no version in your code is not sent. Set value_wo_version only when you want the first apply to write your value.

Each resource page lists its import id.

Use it from CI

A CI job needs the provider, the user key, the secret values and a state backend.

  1. Key. Store the user key in the secret store of your CI system. Expose it to the job as IGNITIFY_API_KEY.
  2. Values. Expose each secret value as TF_VAR_<name>, for an ephemeral variable.
  3. State. Use an encrypted backend with limited access. The state holds hook secrets and user keys.
  4. Steps. Run init, then plan -out, then apply of that plan file. Apply only from your main branch.
  5. Time. A deployment waits for the build, which can take minutes. Set timeouts on the deployment, and a job timeout above it.

Warning

Never run the owner key in CI. Keep the access module out of the pipeline, or apply it by hand.
