Pass state between runs

A run does not see the run before it. To carry state from one run to the next, pick one of three ways. Each is a short pattern, with its limits.

Which one to use

WayWhere it livesPlanUse it whenRead
1 · From outsideThe last result. Your script passes it on as the next payload.Any planSomething outside starts each run anyway: a script, a CI job or your server.From outside
2 · Warm memoryThe memory and the home folder of a warm VM.Starter and upYou want a cache that makes the next run faster, and you can lose it at any time.Warm memory
3 · Own databaseYour database, over its HTTPS API.Starter and upThe state is larger than 10 KiB, you cannot lose it, or runs started together share it.Own database

Try it

The tutorial Pass state between runs builds all three ways step by step, with tasks you can run: From outside Warm memory and Own database.

1 · From outside

Use it when something outside starts each run anyway. The task returns its state as its result, and the caller reads the newest completed result and sends it as the next payload.

Plan: any plan.

  1. The task returns its state as its result. The state is at most 10 KiB.
  2. Before each run, read the newest completed result of the task.
  3. Send that result as the payload of the next run.

run:list lists the newest run first, so --limit 1 gives the newest run that completed. Before the first run there is no result, and jq gives {}. A result of null cannot be a payload.

Limits

  • Two runs at once read the same state. Both continue from the same result. A schedule skips a slot while its last run is still active (overlap: skip, the default); keep it. Otherwise make the work safe to do twice, or use your own database.
  • "Newest" means started last, not ended last.
  • A failed, cancelled or timed-out run saves no state. The next run repeats its work, so make the work safe to do twice.
  • A deleted run drops out. The state can go back to the run before it.
  • A new deployment reads the same state. The read is by task name, so keep a version field in the state.
  • A busy API server answers 503, or 429 over your plan's request rate, with Retry-After. Wait that long and try again.

2 · Warm memory

Use it when you want a cache that makes the next run faster. With state: across-runs, the task process stays alive on a warm VM after a run. The next run of the same task on that VM can read what the last run left in memory and in its home folder.

Plan: Starter and up. Best effort: the VM is lost after a short idle time, about 30 seconds today. Do not depend on it.

  • Runs one after another can share it. Each VM runs one run at a time, so runs started together get separate VMs and separate memory.
  • Files that a run writes in its home folder stay while the process lives, and go with it. With state: independent (the default), each run starts with an empty home folder.

You can lose it at any time

The state is lost after a short idle time, when the process ends (it exits or crashes), when a run hits its time limit or you cancel it, after a new deployment or a change of preset or execution, and when your plan's warm-VM limit is full. A run that fails with an error keeps it. Anything you cannot lose goes in the result (way 1) or in your database (way 3).

3 · Own database

Use it when the state is larger than 10 KiB, when you cannot lose it, or when runs that start together share it. Each run reads the state, changes it and writes it back with compare-and-set: the write succeeds only if nobody wrote since the read. If somebody did, read again and try again.

Plan: Starter and up, because the task needs outbound network.

HTTPS on port 443 only

With egress_allow, the task reaches only the hosts on the list, over HTTPS on port 443. Use your database's HTTPS API. A native driver on another port, for example 5432 or 3306, needs outbound network with no egress_allow list. Keep the store's address and token as secrets.
  • Retry on 429 and 503 after the Retry-After time, a few times.
  • Open the client once per process, not once per run. Each VM opens its own connections, so size your database for runs that start together.
  • A run's traffic leaves from the VM host that runs it, and the address can change. Do not depend on an IP allowlist; use a token.
