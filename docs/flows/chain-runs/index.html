Build flows

Chain runs

A run does one step. Something outside the VM starts the next step: the caller, your own workflow tool, cron job or queue, or the API server when a run ends. A run never starts a run.

1 · The next step in the result

Use it when the next step depends on what the task found. The task returns the next step in its result: which task, and which payload. Or it returns "done". The caller reads the result and starts that step.

Plan: any plan.

  • The result is at most 10 KiB. Pass a reference to your own storage, not the data.
  • A run that fails returns no next step. The caller decides: try again, or stop the flow.
  • This is also how you branch and loop. See Flow shapes.

2 · Your own orchestrator

Use it when the flow has more than a few steps, or when a lost step costs you. Your workflow tool, cron job or queue keeps the state of the flow. It starts each step, waits for its end, and starts the next one. Ignitify is the secure compute step that your tool calls.

Plan: any plan.

How your orchestrator waits for a step

  1. Follow the run until it ends (task:run with wait).
  2. Read its status from time to time (run:get).
  3. Get a callback when the run ends, at your own small receiver. See Get a callback when a run ends.

3 · Run B when A ends

Use it when task B needs to know only that a run of task A ended. Task A's end-of-run callback goes straight to task B's webhook, with no server of yours in between. B starts with A's run id and status as its payload. B does not get A's result.

Plan: Starter and up.

Set it up

  1. Create a webhook for task B (hook:create). Keep its URL and its secret.
  2. Set the callback of task A's deployment to that URL, with B's webhook secret as the signing secret (notify:set).
  3. In task B, read status from the payload. If it is not COMPLETED, stop.

Limits

  • B gets no result from A. The payload holds A's run id, its status, its deployment id and your tenant id. Put data that B needs in your own database. Do not read A's result through the API from inside a VM.
  • It runs on every end of A: COMPLETED, FAILED and CANCELLED. B checks the status first.
  • The callback belongs to one deployment. A new deployment of A starts with no callback. Set it again after each deploy.
  • A lost callback means no run of B. The API server tries again for a time, then gives up and tells you with a callback.failing notification. A refused webhook raises hook.refused. When a lost step costs you, use your own orchestrator.
  • No circles. A callback from B back to A runs forever.
Related
  • hook:create
  • notify:set
  • notification:list

Keep the flow together

  • Put a flow id in the payload and the result of every run.
  • Start each step with an idempotency key made of the flow id and the step. A retry after a network error then starts no second run. After a failed run, a new try is a new run, with a new key. See Retry a run safely.
  • The platform retries only its own failures. Your orchestrator retries a failed step a few times, then stops the flow. See Reliability.
  • Make each step safe to run twice.
  • To keep one version of the code for the whole flow, start each step with the same deployment. A webhook or a schedule uses the newest ready deployment.
