Install & sign in

Install the CLI, sign in once with your Google account, and check that it works. It takes three steps.

1 · Install the CLI

You need Node 22.13 or newer, on macOS or Linux (WSL included). Windows is not tested. The CLI is an npm package named ignitify.

In CI, or for one command, run a pinned version with npx:

Note

The line after the version tells you the CLI reached the platform. It can end with (minimum client …).

2 · Sign in

A new account starts on the free plan, with no key. The CLI gets its key when you run ignitify login and approve it in your browser.

The CLI also opens the page in your browser. Do these steps there:

  1. If the page asks, sign in with Google. The first sign-in creates your account on the free plan.
  2. Compare the code on the page with the code in your terminal. They must be the same.
  3. Choose Approve. Choose Deny if you did not run ignitify login yourself.

The terminal then prints the line that starts with ✓ Signed in.

No browser on this machine

Run ignitify login --no-browser. The CLI prints the page and does not open it. Open the page on any device that has a browser.

The code is short-lived

The code works for 10 minutes. If it expires, the CLI says so. Run ignitify login again.

Name the key

Each machine has one key. Its label is the host name of the machine. Use --name to choose another label, for example when two machines have the same host name.

A second login with the same label replaces the old key. The old key stops working. Your plan limits the number of keys, and the limit counts every key, the keys of your users too: free 2, starter 5, team 10, pro 25 and enterprise (on request) unlimited. If your account is at its key limit, the approve page asks you to pick the key to replace.

3 · Check it works

ignitify whoami shows your workspace, your plan and what you use. More lines follow the part shown here.

If you are not signed in, a command stops with this message:

Your account page

Open account.ignitify.dev/web/profile and sign in with Google. The page shows:

PartWhat it shows
WorkspaceThe name, the id (tnt_…), the status and the plan of your workspace.
Plan limitsA table of what your plan allows: tasks, running VMs, pinned VMs, image storage and scratch storage per VM.
KeysEach key with its label, id, when it was last used, when it expires, when it was created and how it was issued. Choose Revoke to stop a key at once.
Use the CLIThe command ignitify login, where the CLI saves your key (~/.config/ignitify/credentials.json), a short list of useful commands and links to these docs.

The page never shows a key

The account page lists keys but never shows the secret. A key goes to your machine only through ignitify login. If you lose a key, revoke it on the page and run ignitify login again.

Choose Sign out on the page to end your browser session. This does not revoke any key.

Sign out of the CLI

ignitify logout revokes the key of this machine, then deletes the saved file.

If the platform cannot be reached, the CLI still deletes the file. It then warns you that the key may still work, and exits with code 1. Revoke the key on your account page.

Note

If the IGNITIFY_API_KEY environment variable is set, ignitify logout does not change it and does not revoke it. It prints a note.

Where the key is stored

The CLI saves the key in ~/.config/ignitify/credentials.json. If XDG_CONFIG_HOME is set to an absolute path, the file is $XDG_CONFIG_HOME/ignitify/credentials.json. Only you can read it (mode 0600), and only you can open its folder (mode 0700). The CLI refuses a file or a folder that is a link or that belongs to another user, and a file that other users can read.

The key lasts 90 days without use. Each use renews it. It is tied to the server that issued it, so the CLI never sends it to another address. The CLI sends a key only over https, or over plain http to this machine (localhost, 127.0.0.1, ::1).

Upgrade

Upgrade to 3.2

CLI 3.2.0 removes and renames no flag. Run npm install --global ignitify@latest, then note these changes:

  • Recurring schedules. schedule:create <task> --cron "<expr>" starts a run of the task's newest READY deployment at each slot of a 5-field cron expression. --tz sets the IANA time zone (default UTC). It takes the run options of task:run (--payload, --preset, --timeout-sec, --deadline-sec). --overlap skip (the default) starts nothing while the last run of the schedule is still active; --overlap allow starts the run.
  • schedule:show prints one recurring schedule: its state, its run settings and its next fire times.
  • schedule:pause and schedule:resume stop and start a schedule. A resumed schedule fires from its next slot. It does not catch up the slots it missed.
  • schedule:preview <cron> prints the next fire times (in UTC) and makes no schedule.
  • run:list --schedule <sch-id> lists the runs that a schedule started.
  • schedule:list shows both kinds: one-time (task:run --at) and recurring. schedule:cancel deletes a schedule of either kind, and asks first.
  • whoami and quota show the monthly outbound data of a plan with no outbound network as "not included in this plan".

Each new command takes --json. See Run later.

Upgrade to 3.1

CLI 3.1.0 changes no flag. Run npm install --global ignitify@latest, then note these changes:

  • An error from the server prints its sentence and its code, like secret not found [secret-not-found]. With --json a script still gets the raw body.
  • hook:list prints a line on stderr that names the deployment the webhooks run now.
  • deployment:get and deployment:list show admitted_at, the time of the latest build request.
  • task:run without local state runs the task's newest deploy request, and task:get lists deployments in the same order.
  • task:deploy warns when it reuses an older deployment while a newer one is READY, because webhooks still run the newer one.
  • .ignitifyignore and task.yaml must be regular files. A link or a special file is refused.

Upgrade to 3.0

CLI 3.0.0 is a major release. Check your scripts for this change:

  • hook:create and hook:list take a task (its slug or id), not a deployment id. A hook now belongs to the task, so a code update keeps its URL and secret. The --task-name option is removed.

3.0.0 also makes task:create bring back a task you deleted with the same slug, and shows execution in deployment:get.

Upgrade to 2.0

CLI 2.0.0 is a major release. Check your scripts for these two changes:

  • The CLI talks only to the API address that is built into it. The old hidden flag that set another address is removed, and a command that has it is refused as an unknown flag. So your key cannot be sent to another host.
  • run:logs --json and deployment:logs --json now print a JSON document. Before, they printed the raw output. A script that reads the raw logs must drop --json, or read the document.

2.0.0 also adds users, groups and keys, task:run --idempotency-key, run:timeline, run:logs --follow, usage:series and run:failures. 2.0.1 fixes small bugs in key:create and in the help text.

Keys for CI and other people

A key from ignitify login is an owner key: it can do everything. For CI, a script, a team member or an AI client, make a user key with only the permissions it needs. See Users, groups and permissions.

The CLI reads the IGNITIFY_API_KEY environment variable first. If it is set and not empty, the CLI uses it instead of the saved key.
