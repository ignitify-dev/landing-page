Guides

Run later

Start a run at a set time with --at, or on a repeat with a cron expression. List the schedules and cancel one with schedule:list and schedule:cancel.

1 · Schedule the run

Give --at a future time in ISO-8601, in UTC when it ends with Z.

Note

A time in the past is refused with at must be in the future.

2 · List the pending runs

schedule:list shows each pending schedule, soonest first, then your recurring schedules.

3 · Cancel one

schedule:cancel asks first; -y skips the question, and a script needs it.

4 · Do not combine it with --wait

A scheduled run has no run id until it fires, so the CLI refuses --at with --wait.

5 · Find the run after it fires

When the time comes, the schedule leaves the list and the run shows up in run:list.

Note

Cancelling a schedule that has fired, or is firing now, fails with exit code 1. Then look for the run instead.

6 · Run it on a repeat

To run a task every day or every hour, create a recurring schedule with schedule:create and a cron expression. Check the expression first with schedule:preview. It prints the next fire times in UTC and makes no schedule.

Then create the schedule. At each slot, the platform starts a run of the newest READY deployment of the task. The expression has five fields: minute, hour, day of month, month and day of week. --tz sets the IANA time zone, and the default is UTC.

  • The run options --payload, --preset, --timeout-sec and --deadline-sec work here. Every run of the schedule uses them. Without --preset or --timeout-sec, a run uses the value the deployment stored from its task.yaml. Without --payload, the payload is .
  • --overlap skip is the default. A slot starts nothing while the last run of the schedule is still active. With --overlap allow, the slot starts a run anyway.
  • schedule:list shows one-time and recurring schedules. schedule:show <sch-id> shows one schedule with its next fire times. See the runs it started with run:list --schedule <sch-id>.

7 · Pause, resume and delete

schedule:pause stops a schedule from firing. A run that already started goes on. schedule:resume starts it again from its next slot. It does not catch up the slots it missed while it was paused.

schedule:cancel deletes a recurring schedule. The runs it started stay. After many failed slots in a row, the platform pauses the schedule and sends a notification. Find the cause in pause_reason of schedule:show --json, fix it, then resume.

The plan limit

Recurring schedules come with a paid plan; the Free plan does not include them, and a create there is refused with capability-denied. If you move to the Free plan, your schedules stay, but none of them runs: at its next slot each one is paused (pause_reason plan-limit) and you get a notification. A resume on the Free plan gets the same refusal. After you move to a paid plan again, resume them. Your plan limits how many schedules you keep, and a paused schedule counts too. whoami shows max_schedules. The runs of a schedule count against your run limits like any run. See Pricing.

8 · Read the slot in your task

Each run tells your task which run it is and, when a schedule started it, which slot it serves. ctx.run.id is the run_… id of the run, the resource_id that run:get shows. ctx.run.schedule_id is the sch_… id of the recurring schedule, and ctx.run.scheduled_for is the slot time in UTC (ISO-8601, with milliseconds). For a run that no schedule started, both are null.

  • Python: ctx.run.id, ctx.run.schedule_id and ctx.run.scheduled_for; the two schedule fields are None for a run no schedule started.
  • Go: ctx.Run.ID, ctx.Run.ScheduleID and ctx.Run.ScheduledFor; the two schedule fields are "" for a run no schedule started.
  • Rust: ctx.run.id, ctx.run.schedule_id and ctx.run.scheduled_for; the two schedule fields are Option<String> and None for a run no schedule started.
  • Use (schedule_id, scheduled_for) or ctx.run.id as your idempotency key when the task writes to another system. A platform retry of a run keeps its id.
  • Go and Rust tasks get ctx.Run and ctx.run from the client in their ignitify/ folder. Take it from CLI 3.5.0 or later: create the task again with task:create, or copy ignitify/ from a new one, then deploy.

A one-time run has no slot

A run you start with --at gets schedule_id and scheduled_for both empty, although schedule:list shows a sch_… id for it. Use ctx.run.id as the key there.

9 · Run a past slot by hand

To test a schedule, or to run a missed day again, start one run with task:run and put the slot time in the payload. A run that you start has no schedule, so ctx.run.scheduled_for is null. Let the task read the slot from the payload first.

Find the payload of an earlier run of the schedule. run:get --full shows it under payload. No schedule command shows the payload, so with no earlier run, use your own copy.

The schedule runs the newest READY deployment of the task. hook:list names it on its last line. Pass it with --deployment, and give the run an idempotency key, so a retry after a network error starts no second run.

  • The run uses the preset, the time limit and execution that the deployment stored from its task.yaml, as a slot does. A slot also uses the run settings of the schedule (run_settings in schedule:show --json). If the schedule sets a time limit, pass the same --timeout-sec.
  • Without --deployment, task:run uses the deployment in the local state of the folder. That can be another deployment than the one the schedule runs.
  • For 24 hours, a key returns the first answer and starts nothing new. If the run failed, use a new key to run it again.

10 · Missed slots

When the platform is down for longer than the start deadline of a slot, that slot does not run. You get a schedule.missed notification with the reason deadline-passed: "the platform was late and skipped it". After a long delay, only the newest due slot starts.

The skipped slot does not run by itself. If you need it, run it by hand (step 9).

11 · Tell schedules apart

schedule:list shows the task name of each schedule. schedule:show shows one schedule: its task, cron expression, time zone and state. A notification names the sch_… id, so use it here.

Two schedules of one task with the same cron expression differ only in the payload. payload_sha256 in the JSON is the digest of the payload, so compare it.

12 · End a schedule on a date

A schedule has no end date. Cancel it on the day: from a reminder, a CI job, or a Terraform destroy. A month range in the expression stops it inside one year, for example 0 3 * 1-3 * runs only from January to March.

13 · Resume after a platform incident

A long platform incident can make the platform pause your schedules: status is auto_paused and pause_reason is consecutive-misses. After the incident, resume only the schedules it paused. Put the start of the incident, in UTC, in the filter, so a schedule paused before it for another cause stays paused.

A pause and a resume ask no question, so the loop runs in a script. A resume checks your plan again, and it does not catch up the missed slots. Run the slots you need by hand (step 9).
