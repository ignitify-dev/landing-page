Users, groups and permissions

Give each person, CI job or AI client its own key. Each key gets only the permissions it needs, and you can revoke it alone. You need CLI 2.0.0 or later.

Owner keys and user keys

KeyWhat it can do
Owner keyEverything. It is the only key that manages users, groups and keys. You get it from ignitify login.
User keyIt belongs to one user. It has the permissions of that user's groups, and nothing more. The owner makes it with ignitify key:create.
  • A user has a name only. A user has no password, no email and cannot sign in.
  • A user's permissions are the union of the permissions of all its groups. A user in no group can only run whoami and the commands that need no key.
  • Only an owner key can run the user:*, group:* and key:* commands. A user key cannot change its own access, so it can never lock the owner out.
  • A user key does not expire. It works until you revoke it, or remove its user.

The permissions

A group grants permissions from a fixed list of 13. You cannot make a new one. Read and write are separate for each resource, and a delete is a write.

permission:list needs no key and sends no request. Four permissions reach further than their name:

Read these before you grant

  • secrets.read lists secret names only. But deployments.write plus runs.write can read secret values: a user can deploy code that prints its environment, then run it. Treat that pair as access to your secret values.
  • hooks.write can start runs, because a webhook trigger starts a run. It can also send run results to any URL (notify). Grant it only where runs.write is acceptable too.
  • schedules.write can start runs later with no further act, and a schedule outlives the key that made it. task:run --at needs it as well as runs.write. Grant it only where runs.write is acceptable too.
  • tasks.write can delete a task. That also deletes its deployments and runs, and stops their VMs. Grant it only where deployments.write and runs.write are acceptable too.

1 · Create a group

Do these steps with your owner key. Name the permissions, separated by commas.

A user or group name is 1 to 63 lower case letters, digits and -, and starts with a letter or a digit. The CLI checks names and permissions before it sends the request. To change a group later, use group:grant and group:revoke.

2 · Create a user and add it to the group

A user can be in more than one group. user:get shows its groups, its permissions and its live keys.

3 · Create a key for the user

Write the key to a new file with --out. The file gets mode 0600, and the CLI prints only the key id.

  • --user and --label are required. The label tells you later where the key is used.
  • --out writes a new file only. It never writes over a file and never follows a link. If the file exists, no key is made.
  • Without --out, the CLI prints the key on the terminal.

The key is shown once

You cannot read a key again. Give the key to its holder by hand, then delete your copy. If a key is lost, revoke it with key:revoke and create a new one.

4 · Use the key

The holder puts the key in the IGNITIFY_API_KEY environment variable. The CLI uses this variable before a saved login.

whoami shows the This Key block: the key, its user (owner for an owner key), its groups and its permissions.

When a key is refused

A user key that does not have the permission gets permission-denied. The message names the permission, so the holder knows what to ask for.

A user key on a user:*, group:* or key:* command gets owner-required.

Revoke and remove

  • key:revoke <key-id> stops one key at once. key:list shows each key with its user, label and last use, never the key value.
  • user:remove <name> revokes all keys of the user and removes it from all groups. You can use the name again.
  • group:remove-user and group:delete take permissions away. Users and keys stay.
  • A change has an effect on the next request of the key.
  • A revoked key stops, but what it made stays live: schedules, webhooks and callbacks. See the next section.

After a key leaks

Revoke the key first. A revoke changes only the key. The schedules, one-time schedules, webhooks and callbacks that the key made stay live, and their runs use your code and your secrets. Do each step below with your owner key.

  1. Revoke the key. key:revoke stops it on its next request.
  2. Pause its recurring schedules. A recurring schedule shows created_by, the key that made it. A pause asks no question, so it runs in a loop. Check each one later, then cancel it or resume it.
  3. Cancel the one-time schedules made after the leak. A one-time schedule does not record its key, so use created_at and the time the leak can have started (UTC). A cancel asks first, so a loop needs --yes.
  4. Check the webhooks. A webhook call needs its signature, not a key, so a webhook works after the revoke. Run hook:list for each task, and delete each hook you did not make with hook:delete.
  5. Check the callbacks. A key with hooks.write can send the result of every run to its own URL. deployment:get --json shows notify_url. Clear a URL you do not know with notify:set --clear.

Not at the same instant

A slot can fire between the list and the pause, so expect at most one more run of each schedule. On a plan with no monthly limit, nothing caps the cost of what the leaked key left behind, so do these steps at once.

The key limit

Your plan limits the number of live API keys. The limit counts every key: owner keys and user keys together. The limits are: free 2, starter 5, team 10, pro 25 and enterprise (on request) unlimited.

When you are at the limit, key:create is refused. Revoke a key you no longer use, or remove its user. See Pricing and Watch usage and limits.

Example · A read-only AI assistant

An AI client can read your tasks, deployments, runs and usage, but cannot change anything.

Put the key only in the environment of the AI client, as IGNITIFY_API_KEY. Use an AI client tells you how.
