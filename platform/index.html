Three boundaries, each verified separately.

Tenants don’t share a kernel, a uid, or a network path. Each boundary was tested on its own, because a boundary you haven’t tested is a boundary you’re assuming.

The jailed hypervisor

bounds what a hypervisor escape reaches

A per-VM uid, never shared between two live VMs, chrooted to that VM’s files only. Enabled by default in every environment — the production launch path is the only launch path.

The MicroVM

bounds the guest’s reachable network

Separate kernel, three drives, no shared filesystem. Cross-tenant and guest→host traffic are both dropped on two independent paths.

The de-privileged child

bounds what the guest can do

Your code runs as uid 10001 with --no-new-privs. Unconditional — there is no configuration that turns it off.

Concepts

Four levels, each owning exactly one thing.

tenantidentity
An account, and the unit of isolation and auth. Owns hashed API keys, the granted tier, the secrets vault, the monthly egress rollup — and no policy of its own. Everything a tenant may do comes from its tier, and nowhere else.
taska name
A reusable definition, unique per tenant by slug. Slugs are burn-forever: permanently reserved even after deletion, so a deleted name can never be silently reused by something new.
deploymentan image
One immutable, content-addressed build. Owns the resolved execution nature and the bootable code image. Identical content deduplicates instead of rebuilding.
runone job
One execution of one deployment, in one MicroVM. Owns the payload, an immutable instruction snapshot, the boot fingerprint, its slot and IP, and its own per-run callback token and secret.

One run, end to end.

What happens between task:run and a result. Four participants, and three checks that can stop it — each answering a different question.

  1. 1 task:run Submitted with your API key and a payload. It lands on a load balancer — either brain can answer, and neither is the one you talk to next.
  2. 2 May this tenant ask? Reads the tier. Refuses with 429 — the fix is a different tier, not a retry.
  3. 3 Is this kind of work allowed? Capability check. 403 here is the real authority; 400 already caught it at deploy, before any VM.
  4. 4 Admit · record Concurrency, rate, the run row and the month's counter — one transaction against a database on its own machine, so two brains racing the same tenant cannot both win. 503 means the fleet is full: a run inside its entitlement is queued, not refused.
  5. 5 Spawn · network policy Over mutual TLS. The policy is signed and travels with the spawn — a VM never boots into a host that has not been told what it may reach.
  6. 6 Program the kernel A Rust daemon owns every privileged call: the per-slot firewall, the egress allowlist, bandwidth and connection limits. Enforcement is in the kernel, not in your process.
  7. 7 Boot A jailed Firecracker process under its own uid. Separate kernel, read-only code image, read-write scratch.
  8. 8 Pull payload · push result The guest opens every exchange, over vsock — never the network. It asks for its payload, runs your exported function, and streams progress and the result back the same way.
  9. 9 Relay · teardown The host relays the frames it cannot read to the control plane. The VM is destroyed, its slot returned to the pool, and the bytes it sent are billed from the kernel's own counters.
  10. 10 run:get Status, result, and the last streamed chunk — from whichever brain answers, not the one that ran it.

Ignitify runs on bare metal.

Firecracker needs direct access to the CPU's virtualisation — it opens /dev/kvm on the host — so there is no other tenant's hypervisor underneath yours. The boundary around your job is the machine's own, not a scheduler's promise.
