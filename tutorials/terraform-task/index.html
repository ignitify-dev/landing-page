Run a task with Terraform

Set up a tenant only with Terraform, in two folders with two keys, and end with a running task. You make access, a secret, a task with its code and a hook, run it, change it, and clean up.

What this tutorial proves

  • One owner key makes access (a user, a group and a key). A user key then manages the app. A user key cannot make access.
  • The secret value never enters the Terraform state.
  • A code change is one in-place change in the plan, and the hook URL stays.
  • A secret rotates with no redeploy.
  • You can import an object that already exists, and clean up in reverse order.

What you build

Two Terraform folders, each with its own state and its own key, and one task folder.

The access folder makes a user, a group with its permissions, and a key for the user. The app folder uses that key to make the secret, the task, its code (a deployment) and a hook. Keep the folders apart, so the daily job never holds the owner key. Manage a tenant with Terraform explains why.

1 · What you need

  • Terraform 1.11 or later. The secret resource uses a write-only argument. OpenTofu works too, with the full source address (see Provider configuration).
  • An owner key, from ignitify login. See Install.
  • The ignitify CLI. This tutorial was run with 3.1.0.
  • A plan that allows webhooks and outbound calls. This tutorial uses Starter. If ignitify_hook fails, run ignitify whoami and check may_use_webhooks.

8 · Call the hook with a signed request

The hook is a URL that starts a run. A request must carry an HMAC-SHA256 signature of its body, made with the hook secret. Take both from the outputs. Send the body with --data-binary and the JSON content type. With -d, curl labels the body as a form, and the signature check answers 401 invalid-signature.

Each call needs a new x-ignitify-delivery value. A repeat is deduplicated. The run returns version: "B". See ignitify_hook.

10 · Clean up, in reverse order

Destroy the app first, and then access. Access needs the owner key again.

The first destroy removes the hook, the secret, the deployment and the task. The second removes the key, the group and the user. After both:

  • The hook URL answers 404 {"error":"unknown hook","reason":"hook-not-found"}.
  • GET /tasks/terraform-demo answers 404 task-not-found.
  • The user key is refused with API key is unknown or has been revoked [key-invalid].

Keep these in mind

  • The state holds secrets. The access state holds the raw key of the user. The app state holds the hook secret. The secret value itself is never in it. Add .terraform/ and *.tfstate* to .gitignore, and use an encrypted backend with limited access.
  • The CLI after a Terraform setup. task:run and run:get work with the user key. task:get reads only the local task folder, so use ignitify task:list for the server side.
  • Pass the flags as separate quoted words, for example -var "task_dir=$ROOT/tasks/terraform-demo". In zsh, an unquoted variable that holds several flags is not split, and Terraform answers flag provided but not defined.
  • Without the right permission, a run is refused. With runs.read only, task:run answers permission denied: this key needs the runs.write permission.
