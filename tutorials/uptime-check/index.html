Check a website every 10 minutes

A recurring schedule runs a small task every 10 minutes. Each run knows the slot it serves, a down site fails the run so you get told, and you learn to pause, change, re-run and stop a schedule.

What this tutorial proves

  • A recurring schedule starts a run at each slot of a cron expression, in the time zone you choose. No server or cron of your own.
  • Each run knows which slot it serves (ctx.run.scheduled_for), so one slot can write once.
  • A failed run tells you (a notification), and it does not stop the schedule.
  • You can change, pause, resume and stop a schedule, and run one past slot again by hand.

What you build

A small uptime check. Every 10 minutes the task asks one web page for an answer and times it.

  1. At each slot, the platform starts a run of the newest READY deployment of the task.
  2. The task sends one HTTPS request to your page and measures the time.
  3. An answer of 2xx or 3xx within the time budget is "up". The result holds the slot, a key for the slot, the status and the time.
  4. "Down" or "slow" fails the run. You see it in run:list and as a notification.

Before you start

  • A plan with recurring schedules and outbound access. This tutorial uses Starter. The Free plan has no recurring schedules: a create there is refused with capability-denied. whoami shows max_schedules.
  • The CLI, installed and signed in. See Install.
  • Room in your run limits: a run every 10 minutes is 144 runs a day, and each counts like any run. quota shows your limits.
  • A page to check. The example checks https://example.com/.

Create the task

Replace the files the command made with the files below.

The code

slotOf in utils.ts reads the slot. A run that a schedule started has it in ctx.run.scheduled_for, a UTC time such as 2027-01-15T02:00:00.000Z. The key sch_…:<slot> names that slot once. Use a key like this when the task writes to another system, so a retried run does not write twice. A run that you start yourself has no slot: schedule_id and scheduled_for are null, and the key is the run id.

Allow the host you check

The request goes only to a host in egress_allow. To check your own page, put its host in task.yaml and its URL in run.payload.url and in the schedule's --payload. A host that is not in the list fails the run.

Validate, deploy and run it once

The result has slot: null and a key that is the run id: you started this run, not a schedule.

Check the cron expression

The expression has five fields: minute, hour, day of month, month and day of week. */10 * * * * means "at minute 0, 10, 20, 30, 40 and 50 of every hour". schedule:preview prints the next fire times in UTC and makes no schedule.

A daily check at 09:00 in Berlin would be "0 9 * * *" with --tz Europe/Berlin. The zone follows summer and winter time. Without --tz the expression reads in UTC. The fastest repeat is once a minute.

Create the schedule

Keep the sch_… id. The run options --payload, --preset, --timeout-sec and --deadline-sec work here, and every run of the schedule uses them. Without --preset or --timeout-sec, a run uses the deployed task.yaml values (std.micro, 30 seconds). The schedule does not use run.payload of task.yaml: without --payload the payload is , and this task needs a url.

Overlap

With --overlap skip, the default, a slot starts nothing while the last run of the schedule is still active. With --overlap allow, it starts a run anyway. For a check of 30 seconds every 10 minutes, the two are the same.

The payload is replaced

A new --payload replaces the whole payload, and the old one cannot be read back. Only the fields you give change, and the schedule keeps its id, its runs and its state.

When a slot cannot start

A slot is "missed" when it does not start a run. The common causes:

  • No READY deployment of the task, or a run setting your plan does not allow.
  • Your own limits, for example your running VMs are all in use by your own runs. The slot waits and tries again. If its time passes, it is missed.
  • A long platform delay. You get a schedule.missed notification with the reason deadline-passed. After a long delay, only the newest due slot starts.

After 10 counted misses in a row, the platform pauses the schedule: status is auto_paused, and you get a notification. A wait caused by the platform, such as a host in maintenance, does not count. Find the cause in pause_reason, fix it, then resume:

Pause and resume

A pause stops new slots. A run that already started goes on.

A resume starts again from the next slot. It does not catch up the slots it missed while it was paused. A paused schedule still counts toward max_schedules.

Run one past slot again

To check a slot again by hand, start one run with the slot in the payload. A run that you start has no schedule, so the task reads payload.slot first. With schedule_id in the payload too, the key is the same as the schedule's key for that slot.

  • The run uses the preset, the time limit and execution that the deployment stored from its task.yaml, as a slot does. A slot also uses the run settings of the schedule (run_settings in schedule:show --json). If the schedule sets a time limit, pass the same --timeout-sec.
  • For 24 hours, an idempotency key returns the first answer and starts nothing new. To run a failed slot again, use a new key.

Deploy a change

Change the code and deploy again. The schedule keeps its id, and its next slot runs the new deployment, because each slot runs the newest READY deployment of the task. You do not create the schedule again.

End-of-run callbacks

If you get a callback when a run ends (notify:set), set it again after each deploy: a new deployment starts with no callback. From CLI 3.6.0, task:deploy warns you and prints the command.

Clean up

schedule:cancel deletes a recurring schedule. The runs it started stay.
