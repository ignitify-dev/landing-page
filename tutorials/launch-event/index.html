CLI version

You need ignitify CLI 1.2.2 or later for integration:add. The outputs on this page come from real runs. See Integrations.

What this tutorial shows

  • Each integration shows a plan and changes nothing before you say yes.
  • A task with no network gets no open egress: egress_allow holds only the hosts that you add.
  • A value that conflicts is refused, never overwritten. The network type and the preset are only raised, and lists are joined.
  • A host that is different for each user is left for you to add ("you add").
  • task:validate finds a hand edit that breaks an integration, before you deploy.

What you build

A task for a product launch:

  1. It gives the viewer link in the run's progress, two minutes before the stream starts.
  2. It streams the launch video live. Viewers open the link in a browser.
  3. When the stream ends, it uploads the recording to your bucket and returns download links.

Two integrations write the settings for this: stream and s3-storage. You write the task code.

The journey

You run a product launch. You want a live video that people can watch in a browser, and a recording in your own bucket after the event. Without help, that is a lot of work that is not your product: a live encoder, a player, a web server, S3 request signing, and the right network and machine settings.

Integrations do that work for you. Each one is a tested package plus the settings it needs. You add it with one command, and you write only what is yours.

~20lines of task code that you write
~800lines of tested code that you do not write
7settings written for you by integration:add

Without integrations, you build

  • The ffmpeg command for live HLS, and a clean stop on cancel
  • A web server, a player page and a video player script
  • S3 request signing, uploads and expiring download links
  • The network, inbound route, machine size and packages, found by trial and error

With integrations, you write

ignitify integration:add stream
ignitify integration:add s3-storage

await stream(ctx, { source: video })
await store.putAndLink(file)

Two commands and two calls are the core of the task. The full code is in step 5.

Why integrations matter

Less code

You keep only your own logic. The hard parts are in packages that are tested and kept up to date.

Correct settings

Each integration shows a plan and writes nothing until you say yes. task:validate finds a hand edit that breaks it, before you deploy.

Safe by default

The network stays closed: you add each host. Secrets are names in task.yaml, never values in your code.

One-command upgrades

Run integration:add again to get the latest version. The plan shows only what is new.

The steps

  1. Create a task. You get a folder with task.yaml and package.json.
  2. Add the integrations. Each one shows a plan of the settings it needs, and writes them when you say yes.
  3. Finish task.yaml. You add two hosts: the host of the video and the host of your bucket.
  4. Write the code. About 20 lines: stream, upload, return.
  5. Deploy and run. Share the viewer link. The recording links come back in the run's result.

Before you start

  • A plan that allows inbound traffic and the std.medium preset. This tutorial uses Pro.
  • The CLI, installed and signed in. See Install.
  • An S3-compatible bucket and an access key for it.
  • The launch video at an https:// address.

On the Team plan

The Team plan also allows inbound traffic and std.medium, but its longest run is 1 hour. Set run.timeout_sec to 3600 or less in task.yaml.

Step 5: Write the code

The code has three parts: stream, upload, return. startDelaySec serves the player page and puts the viewer link in the run's progress before the video starts (120 s by default). after: 'stop' makes stream() return when the video ends, with the recording left on the disk.

The video and the delay come from the payload, so one deployment serves a rehearsal and the real event. The defaults are in run.payload in task.yaml.

The recording

The recording is a playlist file and its segment files. Each file gets its own download link, valid for up to 7 days. The result holds one link: a text file that lists the download link of each file.

Step 6: Store the secrets

Later: upgrade an integration

When a new version of an integration comes out, task:validate warns that your version is obsolete and names the latest one. The warning does not change the exit code.

To upgrade, run integration:add again. It installs the latest version, and the plan shows only the new settings:

Then run task:validate. It now checks task.yaml against the new version. Then deploy.

Clean up

Delete what you no longer need. The files in your bucket stay until you delete them there.
