Live video streaming job

ffmpeg pulls a video from the internet and re-streams it as live HLS from a MicroVM. Anyone with the link can watch, and the run lasts until you cancel it.

What this tutorial proves

  • A task reaches the internet only through an allow-list (egress_allow).
  • A deployment gets its own public HTTPS address, and the task chooses which paths are public.
  • A run can report live progress while it runs (ctx.chunk).
  • A run can last until you stop it, and it stops cleanly on run:cancel (SIGTERM).
  • System tools such as ffmpeg are installed into the image at build time.

What you build

A task that turns any https video into a live stream that anyone can watch in a browser.

  1. The task starts a small HTTP server on port 8080 and tells the platform it is ready.
  2. ffmpeg downloads the video (outbound) and re-encodes it to HLS at playback speed.
  3. Viewers open /live/ on the deployment's public address (inbound).
  4. When the video ends, the task keeps serving it for replay until you cancel the run.

The task's nature

In task.yaml you declare what the task is. The platform decides how to run it.

SettingValueWhy
network.typebidirectionalOutbound to fetch the video, inbound so viewers can connect.
egress_allow[raw.githubusercontent.com]The only host the task may reach. A redirect to another host is blocked.
inbound_port8080The port the task listens on. It must match PORT in index.ts.
inbound_routes/live/Only these paths are public. Everything else answers 404.
interactioncontinuousProgress chunks reach run:get while the run is live.
durationlongThe run lasts until you cancel it, up to timeout_sec.
presetstd.medium512 MiB. Live x264 runs out of memory on std.micro.

Before you start

  • A plan that allows inbound traffic and the std.medium preset. This tutorial uses Pro.
  • The CLI, installed and signed in. See Install.

On the Team plan

The Team plan also allows inbound traffic and std.medium, but its longest run is 1 hour. Set run.timeout_sec to 3600 or less in task.yaml.

Create the task

Register the name and get a task folder with starter files. You replace the starter files in the next step.

The code

index.ts wires the server, the ffmpeg process and the stop signal. utils.ts holds the pure functions, so they are easy to read and to test. The platform bundles both files into one, so a relative import works.

Validate

Check task.yaml on your machine. Nothing is sent and nothing is built.

Ask the platform's AI to review the system packages and estimate the build time. It is advice only and never changes the exit code. Only the package names and the runtime leave your machine.

Deploy

Upload the source. The platform installs ffmpeg, bundles index.ts and utils.ts, and builds the image.

Deploy again after every change to index.ts, utils.ts or task.yaml. Each deployment gets its own public address.

Run and watch

Start a run. The default payload in task.yaml streams a 30 s Big Buck Bunny clip, so no flags are needed.

To stream another video, pass a payload. Add the video's host to egress_allow first, and redeploy.

Find the viewer address. progress holds the last chunk the task sent, and its watch field is the address. The plain run:get view does not show progress, so use --full.

Open the watch address in a browser, or play the playlist with ffplay or VLC:

When the video ends, the last chunk becomes {"status":"ended","replay_until":"run:cancel"}. The run stays RUNNING, and viewers can replay the whole video.

Stop and clean up

A graceful cancel sends the task SIGTERM. The task stops ffmpeg, closes the server and returns {"cancelled": true}. It arrives with the next heartbeat, so it can take about 5 s.

Load test

How many viewers can one run serve? We ran simulated viewers against one run and added more in steps.

  • Viewer: simulated HLS player: 12 s buffer, 3 retries (0.5 s, 1 s, 1.5 s), one connection each.
  • Video: Big Buck Bunny 1080p, 30 s, re-encoded to 480p HLS: 8 segments, about 1–1.8 Mbit/s.

What the numbers mean

  • The task never failed. No test step caused a crash or a connection error. The platform refused extra requests before they reached the VM.
  • Refusals start at about 32 viewers, but nobody notices. inbound_max_concurrent: 16 counts requests at the same instant, not viewers. A viewer downloads a 4 s segment in a fraction of a second, then waits. When more than 16 downloads overlap, one is refused, and the player retries half a second later. Its 12 s buffer hides the wait.
  • Freezes start at 96 viewers, and the cause is bandwidth. Throughput stays flat at the plan's cap of about 100 Mbit/s. Downloads slow down, more of them overlap, retries fail, and a buffer runs empty.
  • So one run serves about 80 viewers at 480p with no freezes. A lower height uses less bandwidth per viewer and raises that number.

Test fleet, not production

These numbers come from our test fleet on dev-class hosts. They show where the limits are, not a guaranteed capacity. Your numbers depend on your plan's bandwidth and the video's bitrate.
