Pass state between runs

A run does not see the run before it. First you send the last result as the next payload, so a counter goes on from 1 to 2 to 3 and a failed run changes nothing. Then you keep a counter in the memory of a warm VM and see when it is lost.

What this tutorial proves

  • A run's result can be the next run's input. The platform keeps every result, and you read the newest one that completed.
  • A failed run saves no new state, so the next run goes on from the last good one.
  • This way has limits: two runs at once read the same state, and a deleted run drops out.
  • A task that keeps state in memory can reuse it on a warm VM, but only as a cache, and only for runs one after another.
  • Runs that start at the same time get their own VMs and do not share that memory.

Which way fits your task? See Pass state between runs. It compares three ways: the last result, a warm VM and your own database. This tutorial builds the first two.

Before you start

  • The CLI, installed and signed in with your own (owner) key: ignitify login. See Install.
  • jq, for the one-line reads below.
  • Part 1 runs on any plan. Part 2 needs Starter and up: the Free plan has no warm VMs. Neither task has a network, and both use the smallest preset.

  • run:list lists the newest run first. --status COMPLETED --limit 1 gives the newest run that completed.
  • Write the status in capitals: COMPLETED. A lowercase status is refused.
  • --json prints a list of runs, and each run has its result.
  • To read one run: ignitify run:get <run-id> --json | jq .result.

A failed run keeps the last good state

The result is count 4. The failed run has no completed result, so the next read skips it.

  • task:run --wait exits with code 1 when the run fails. In a script with set -e, check the status yourself, or the script stops.
  • If you delete a run (run:delete), the next read goes back to the completed run before it.

The limits of this way

Read these before you rely on it

  • Two runs at once read the same state. Both continue from the same result, and both write a result. A schedule skips a slot while its last run is still active (overlap: skip, the default); keep it. Otherwise make the work safe to do twice.
  • "Newest" means started last. The list is in the order the runs started, not the order they ended.
  • A failed, cancelled or timed-out run saves no state. The next run repeats its work, so make the work safe to do twice.
  • Deleted runs drop out. run:delete, deleting a deployment (it deletes its runs) or deleting the task removes those results, so the state can go back.
  • A new deployment reads the same state. The read is by task name. Keep a version field in the state, and start over or convert when it changes.
  • Size. A result and a payload are each at most 10 KiB. A result of null cannot be a payload, so use // {} as above.
  • A busy API server answers 503, or 429 over your plan's request rate, with Retry-After. Wait that long and try again, a few times.

All at once: no sharing

Three runs that start together get three VMs, and each result has count 1. One VM runs one run at a time, so runs that start together do not share memory. Later runs can land on any of the three VMs, so each VM counts on its own. Runs that must share state while they start together need your own database.

Files follow the process

  • With across-runs, files that a run writes in its home folder stay while the process lives, and go with it.
  • With state: independent (the default), each run starts in a new process with an empty home folder, also on a warm VM.
  • Keep files in the home folder. The task cannot write anywhere else, for example in /run.

When the state is lost

CauseState after it
The next run starts after a short idle time (about 30 seconds today; do not depend on it)Lost: a new VM
A run fails because it throws an errorKept: the process lives on
The process ends (it exits or crashes)Lost: the VM ends with it
A run hits its time limit, or you cancel a running runLost: the VM is stopped
A new deployment (a code change, or a change of execution)Lost: a new VM

Start runs from your own code

A run that you start with POST /runs uses the settings of the deployed task.yaml, the same as task:run. A field you send in the call (execution, preset, timeout_sec) wins for that run. So a call with only the payload lands on the warm VM, like the runs above.

Rules for warm memory

  • Treat it as a cache. Anything you cannot lose goes in the result (part 1) or in your own database.
  • Do not depend on the order or the sharing of runs that start together.
  • Keep the state small: it is the memory of one VM.
