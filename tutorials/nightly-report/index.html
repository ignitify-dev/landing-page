Nightly GitHub report

Every night, a short task reads one GitHub repository through its API and returns a Markdown digest of the day. A cron starts it through a signed webhook, and a callback tells your server when the report is ready.

What this tutorial proves

  • A task reads a secret by name (ctx.secrets). The value is never in the code, the config or the command line.
  • A task reaches only the hosts you allow (egress_allow), and nothing can connect in.
  • A run can start at a set time (task:run --at), or from a signed webhook that a cron calls.
  • A repeated webhook delivery returns the same run, so a retried cron job does not start a second report.
  • The platform calls your server when a run ends (notify:set), signed, so you know it is from us.

What you build

A daily digest of one GitHub repository, as Markdown: releases, merged and new pull requests, new and closed issues, and commits.

  1. A cron calls the task's webhook every night, with the repository in the body.
  2. The task reads four GitHub endpoints at the same time, with your token.
  3. It returns the counts and the Markdown report as the run's result.
  4. The platform calls your server. Your server reads the report from the run.

Before you start

  • A plan with webhooks. This tutorial uses Starter. Free allows the secret and the outbound call, but not hook:create or notify:set.
  • The CLI, installed and signed in. See Install.
  • A GitHub token that can read the repository: a fine-grained token with read-only access is enough.

The code

index.ts makes the four GitHub calls at the same time and turns a GitHub refusal into a clear error, so a failed run says what to fix. utils.ts sorts what GitHub returned into the report and keeps it under the 10 KiB result limit: at most 10 items per section, and a note when GitHub returned a full page.

Store the token

Read the value from a file or a pipe, so it stays out of your shell history. A value on the command line is refused.

Run it at a set time

For one run at a known time, use --at with a future UTC time. No run exists until it fires.

One time, not a repeat

A schedule fires once. For a report every night, let a cron call a webhook, as in the next step.

Run it every night

Create a webhook for the deployment. The reply shows the secret once, so store it now.

Put the URL and the secret in your repository's Actions secrets as IGNITIFY_HOOK_URL and IGNITIFY_HOOK_SECRET, and add this workflow. It signs the body and sends one delivery id per day, so a retried job returns the same run.

A good call answers 202 with the new run id. A wrong signature answers 401.

Get told when it is ready

Give the deployment a callback URL and a signing secret of your own. The platform POSTs there when a run ends.
