AI pull-request reviewer

When a pull request opens or changes, a short Go task reads its diff from GitHub, asks Claude for a review, and posts the review as a comment. It starts in mock mode, so you can run it before you have any keys.

What this tutorial proves

  • A task reads two secrets by name (ctx.Secrets). The values are never in the code, the config or the command line.
  • A task reaches only the hosts you allow: here exactly two, api.github.com and api.anthropic.com.
  • GitHub starts a run through a signed webhook, with the repository and the pull request number in the body.
  • A repeated webhook delivery returns the same run, so one commit on a pull request gets one review.
  • A task can post AI output back to the system that called it: the review lands as a comment on the pull request.

It starts in mock mode

The sample runs in mock mode. It returns a built-in sample review and makes no GitHub or Claude call until you set real keys. See Going live.

What you build

A reviewer that comments on every new pull request and on every new commit pushed to one.

  1. A GitHub Actions workflow calls the task's webhook with {"repo":"owner/name","pr":123}.
  2. The task reads the pull request's diff from the GitHub API.
  3. It sends the diff to Claude and gets back a verdict, a summary and a few line comments, as JSON.
  4. It posts the review as one comment on the pull request, and returns a short result.

Before you start

  • A plan with webhooks. This tutorial uses Starter. Free allows the secrets and the outbound calls, but not hook:create.
  • The CLI, installed and signed in. See Install.
  • For mock mode, nothing else. To go live: a GitHub token that can read pull requests and write comments on the repository, and an Anthropic API key.

Create the task

Register the name and get a Go task folder with starter files. You replace main.go and task.yaml, and add review.go, in the next step.

The code

main.go picks the clients and runs the flow. review.go holds everything that makes no network call, so you can read and test it alone. Both files are in package main, and the platform builds them together into one binary.

GitHub and Claude sit behind two small interfaces, GitHub and Reviewer. In mock mode the task uses the mocks in review.go. Otherwise it uses githubAPI and claudeAPI in main.go, which call the real APIs.

The mock rule is one line in review.go: the run is a mock while GITHUB_TOKEN is mock-github-token or ANTHROPIC_API_KEY is mock-anthropic-key. So a run never posts a fake review with a real token.

Store the two secrets

For mock mode, store the sample values. Read each value from a pipe or a file, so it stays out of your shell history. A value on the command line is refused.

Validate and deploy

Check task.yaml on your machine, and list the files that a deploy would upload. Nothing is sent and nothing is built.

Upload the source. The platform compiles the Go module and builds the image.

Run it once in mock mode

The default payload in task.yaml reviews pull request 42 of octo-org/widgets. In mock mode that repository is never called. --wait follows the run and prints it with its result.

Read the result

mock: true says that no GitHub or Claude call was made. With real keys, this is the comment the task posts on the pull request:

A bad payload fails the run with the reason, for example "repo" must be "owner/name". Read it with run:get <run-id>.

Connect GitHub

Create a webhook for the deployment. The reply shows the secret once, so store it now.

Put the URL and the secret in your repository's Actions secrets as IGNITIFY_HOOK_URL and IGNITIFY_HOOK_SECRET, and add this workflow. It sends only the repository and the pull request number, signed with HMAC-SHA256. The delivery id holds the commit, so a re-run job returns the same run instead of a second review.

A good call answers 202 with the new run id. A wrong signature answers 401.

Why a workflow, not a repository webhook

The trigger checks the x-ignitify-signature header. A GitHub repository webhook signs with its own header, and it sends the whole event, which can be larger than the payload limit. The workflow sends a small body that the task needs, signed the way the trigger expects.

Pull requests from forks

GitHub does not give Actions secrets to a workflow that runs for a pull request from a fork. For those, the call has no secret and the trigger answers 401.

Going live

Replace the two sample values with real ones. The platform reads secrets when a run starts, so the next run uses them. You change no code.

  • GitHub token: a fine-grained token for the repository with the Pull requests: Read and write permission. It reads the diff and posts the comment.
  • Anthropic key: from the Claude Console. The task calls the Messages API with claude-opus-5-5 at effort: low, and asks for JSON in the shape of Review.
  • Check it first: run once with --payload on a test pull request, and read mock: false in the result.

Things you may want to change in the code:

  • prompt() in review.go: what Claude looks for, and how many line comments it may give.
  • maxDiffBytes: how much of a large diff Claude reads. The rest is cut, with a note.
  • githubAPI.Comment: post line comments on the diff instead of one comment, with GitHub's pull request review API.

Real keys cost money

Each real run is one Claude request, billed to your Anthropic account. A busy repository can start many runs.
