01 — The console

You don’t configure a runtime. You describe a workload.

  1. You set seven axes

    Cardinality, duration, state, interaction, network, residency, storage. Nothing else.

  2. The platform derives the rest

    VM lifecycle, teardown, worker instructions, network, and the boot fingerprint.

  3. A garbage collector reclaims it

    When the run ends the VM is destroyed and its slot returned to the pool.

02 — Blast radius

Containers share a kernel. This doesn’t.

Every job boots its own kernel inside its own MicroVM. One tenant’s code cannot read another’s memory, reach another’s filesystem, or talk to another’s network — not because a policy forbids it, but because there is no shared surface to cross.

01

Separate kernel

Not a namespace on a shared one. A hypervisor boundary, not a container boundary.

02

Nothing shared

Its own uid, its own root filesystem, its own network path. No two live VMs share any of the three.

03

Verified, not assumed

Cross-tenant and guest→host traffic are dropped at the packet level.

03 — Writing a task

Two files. Export run. That’s the contract.

This is a complete, real task — the whole developer surface in one screen. Note the imports: there are none.

config.ts
export default {
  slug: "STREAMING-JOB",

  execution: {
    cardinality: "one",
    duration: "short",
    state: "independent",
    interaction: "continuous",
    network: { type: "egress" },
  },

  run: {
    payload: { q: "war" },
    timeout_sec: 15,
  },
};
index.ts
export async function run(payload, ctx) {
  const res = await fetch(
    `https://api.datamuse.com/sug?s=…`,
  );
  const json = await res.json();
  const top = json.map((w) => w.word).slice(0, 5);

  for (const [i, suggestion] of top.entries()) {
    ctx.chunk({ suggestion, i });
  }

  return { q: payload.q, count: top.length };
}

Content-addressed

Deployments are immutable and hashed. Redeploying an unchanged bundle reuses the existing image.

Image integrity

The code image is read-only inside the guest. It is verified before boot, not trusted after it.

Secrets

Only secret names enter the bundle. Values are injected at run time and never stored with your code.

05 — Many tenants, one host

One noisy tenant can’t take the host down with it.

Running this for other people is a different job from running it for yourself. The controls for that are first-class, not bolted on.

Tiers, not overrides

Every limit a tenant has comes from a tier they are granted. A one-off deal is a new tier, never an edited row.

Fair queueing

One tenant’s deploy storm cannot starve another’s build. The work queue claims fairly across tenants.

Honest capacity

Entitlement and room are separate ledgers, so “allowed” and “available” are never conflated.

06 — Deploy and scale

Three steps on your machine.
Then one crossing.

No network · no API key Your machine
  1. 01

    task:create

    offline

    Registers the slug and scaffolds config.ts and index.ts.

  2. 02

    task:validate

    offline

    Checks the execution nature and the seven axes. No server, no key.

  3. 03

    task:bundle

    offline

    Compiles and packs a tarball. Still local — nothing has been uploaded.

The wire — crossed once Ignitify
  1. 04

    task:deploy

    crosses the wire

    Uploads the bundle and builds a read-only ext4 image. This is where the API key is first needed.

  2. 05

    task:run

    on the platform

    Boots a MicroVM against that image and executes your run().

  3. 06

    run:get

    on the platform

    Status, result, and the last streamed chunk. Deploy once, then run as often as you like.
